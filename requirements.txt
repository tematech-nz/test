Requirements for Coding Agent
================================

1. PROJECT GOAL

Build a lightweight web application for documenting and visualizing physical network infrastructure: groups, racks, patch panels, switches, wall sockets/endpoints, fixed multi-wire links, and individual patch cables.

The application must provide:
- A free-form map for arranging infrastructure.
- Separate VIEW and EDIT modes.
- Accurate port-level physical connectivity.
- End-to-end physical path tracing.
- Multiple maps for rooms, floors, buildings, or other areas.
- Portable project storage using versioned JSON.
- Offline operation without a cloud account.

This is a physical cabling documentation tool, not a live network discovery or traffic monitoring tool.

2. TECHNOLOGY AND DEPLOYMENT

- Prefer a lightweight, backend-less HTML/CSS/JavaScript application unless a backend provides a clear benefit.
- Python or Node.js is acceptable if needed.
- The application must run locally and work offline during normal use.
- All project data must be exportable to and importable from a human-readable JSON file.
- Browser storage may support autosave, but must not be the only way to save or back up a project.
- Keep the data model independent of canvas rendering and UI code.
- Use stable unique IDs for projects, maps, groups, objects, ports, fixed links, individual wires, and patch cables.
- Include a schema version and migration strategy for future changes.
- Document installation, startup, data format, and backup/restore steps.

3. VIEW MODE AND EDIT MODE

The application must have two explicit modes.

VIEW MODE
- Intended for everyday browsing, especially on smaller mobile phone screens.
- Must be read-only: users cannot accidentally move, delete, rename, or reconnect infrastructure.
- Optimize the layout for narrow screens. Use a responsive layout rather than shrinking the full desktop interface.
- Prioritize search, map/location navigation, object details, port status, and end-to-end tracing.
- Selecting an object, port, fixed link, or patch cable should open a compact details view or bottom sheet.
- Support zoom and pan on the map, but prevent accidental infrastructure edits.
- Make cable tracing and navigation between maps practical on a phone.
- Hide editing toolbars and complex property panels unless needed for viewing details.

EDIT MODE
- Intended for creating and maintaining the infrastructure model.
- Provide object creation, selection, movement, resizing where supported, connection editing, property panels, and deletion.
- Provide clear visual indication that edit mode is active.
- Require an explicit action to enter edit mode; avoid accidental changes while browsing.
- Use desktop-friendly editing controls. On mobile, provide usable touch controls, while recognizing that complex editing may be easier on a larger screen.
- Switching modes must not change project data.
- Include a safe way to return to view mode without losing saved changes.

4. PROJECT DATA MODEL

Represent these concepts separately:
- Project: all infrastructure records and maps.
- Map: a visual view of some or all infrastructure.
- Group: the default container element for organizing equipment.
- Equipment object: rack, patch panel, switch, wall socket/endpoint, or generic object.
- Port: an individually addressable termination on an object.
- Fixed link: a permanent installed cable route/link between patch panels, containing one or more individual wires.
- Fixed wire: one individual conductor, copper pair/circuit, fibre strand, or other individually documented connection within a fixed link.
- Patch cable: a removable cable connecting two specific ports.
- Internal mapping: an explicitly documented physical mapping between terminations, such as the front and rear of a patch panel.
- Map placement: an object's visual position and appearance on a particular map.

Names and canvas coordinates must never be used as identifiers. Moving or renaming an object must not break connections.

5. GROUPS AND CONTAINMENT

A Group must be available as a default container element and be the primary way to organize infrastructure on the map.

- Users can create and name groups, such as a building, floor, room, rack area, cabinet, or network zone.
- A group can contain racks, patch panels, switches, and other supported objects.
- A group may be nested inside another group if this can be implemented cleanly.
- Objects must also be allowed outside groups when appropriate, including a standalone patch panel or standalone switch.
- Group contents should be visually represented within or associated with the group.
- Moving a group should move its visual contents as a unit without changing connectivity.
- Moving an individual object within a group must not move the entire group.
- Deleting a group must not silently delete its equipment or cables. Offer clear choices such as removing the container while retaining its contents, or deleting the contents after confirmation.
- Groups are organizational containers; they must not automatically connect ports or imply physical connectivity.

6. MAPS AND LOCATIONS

Support multiple maps within a project, for example:
- Building overview.
- Floor map.
- Server room.
- Office area.
- Separate network rooms or buildings.

Each map has a stable ID, name, and optional location description. Maps have independent visual layouts and viewport settings.

- The same physical object may appear on more than one map without creating duplicate equipment records.
- Connections must reference the shared project objects and ports, not copies on each map.
- A cross-map connection must be traceable from either end.
- When tracing reaches an object on another map, provide navigation to that map and highlight the relevant object or connection.
- A map may show a high-level overview while another shows a detailed arrangement of the same area.
- Provide map/location navigation that works in view mode on a mobile phone.

7. SUPPORTED EQUIPMENT OBJECTS

7.1 Rack
- Name, stable ID, optional location, description, and optional rack height.
- Can contain multiple patch panels and switches.
- Moving the rack moves its contained objects visually as a unit.
- Equipment inside a rack retains its IDs, ports, and connections when repositioned.

7.2 Patch panel
- Configurable port count and individually editable port labels.
- Can be placed inside a rack, inside a group, or standalone.
- Must not behave like a switch.
- Must support documented internal mappings between front and rear terminations where applicable.
- Do not assume that similarly numbered ports are internally mapped unless that mapping is configured or explicitly established by the chosen panel model.

7.3 Switch
- Can be placed inside a rack, inside a group, or standalone.
- Configurable port count, labels, and optional port type/speed/media properties.
- Common port counts such as 8, 16, 24, and 48 should be easy to create.
- Show free and occupied ports.
- Do not treat a switch's ports as physically cabled to each other merely because they belong to the same switch.

7.4 Wall socket / endpoint
- Configurable number of independently addressable ports.
- Name, ID, and optional location.
- Resizable visual representation without changing port count or connectivity.
- Can be placed within a group or independently on a map.

7.5 Generic object
- Optional name, ID, description, size, and appearance for equipment not covered by predefined types.

8. TWO DISTINCT CABLING OPTIONS

The application must clearly distinguish between these two connection types. They have different editing rules and must not be represented as interchangeable objects.

8.1 FIXED MULTI-WIRE LINK (PERMANENT INSTALLED CABLING)

This represents fixed cabling between patch panels, such as:
- Rack-to-rack permanent cabling.
- Rack patch panel to a standalone patch panel.
- Patch panel to patch panel between rooms or floors.
- In-wall, ceiling, conduit, or inter-rack installed cabling.

A fixed link is a parent object representing one installed cable run or bundle. It contains N individually documented wires. Each wire records its own termination at both ends.

Required behavior:
- Create a fixed link between two patch panels or other explicitly supported fixed-cabling termination objects.
- Configure the number of wires in the link.
- Display the link as one visible route between its two endpoints, with the wire count clearly shown.
- Allow users to open the link and see its individual wires and endpoint mappings.
- Each wire must have a stable ID or wire number, and a source termination and destination termination.
- Support explicit mappings such as panel A port 1 to panel B port 1, panel A port 2 to panel B port 2, or any other manually configured mapping.
- Do not assume the mappings are sequential unless the user explicitly chooses a sequential mapping action.
- Allow individual wires to be documented as unused, spare, connected, faulty, or otherwise configured if status tracking is supported.
- Allow cable type, ID, length, route description, and installation status to be recorded at link level.
- Distinguish the installed link visually from removable patch leads, using a different default line style and/or appearance.
- The fixed link and its individual wire mappings must remain stable when the map layout changes.

FIXED-LINK EDITING RULES
- Treat a fixed link as installed infrastructure, not as an ordinary patch cable.
- Do not allow users to casually drag one endpoint to another port or change wire mappings by moving objects on the map.
- To change the physical endpoints or wiring, the user must explicitly use an operation such as “Replace/Re-run link” or “Edit installed wiring,” with a clear confirmation and change summary.
- Adding or deleting individual wires must be an explicit action within the fixed link, not an accidental consequence of moving or editing the visual line.
- Support an audit-friendly confirmation that identifies the old and new endpoints or the wires being added/deleted.
- Moving a rack, group, panel, or map object must never modify the fixed link's actual endpoints or wire mappings.

The fixed link is a parent record; each wire is a separately addressable connection within that record. The visual line on the map is not the wire data itself.

8.2 PATCH CABLE (REMOVABLE EQUIPMENT PATCHING)

A patch cable represents a removable lead used to connect two specific ports, usually within a rack or around a panel/switch area.

Examples:
- Switch port 12 to patch panel port 12.
- Patch panel port to another patch panel port using a short lead.
- Wall socket port to a nearby device port, if appropriate for the documented environment.

Required behavior:
- Each patch cable is an individual cable object with its own ID.
- Record source object/port and destination object/port.
- Record cable type, colour, optional length, and optional status.
- Create, reconnect, edit, or remove patch cables through explicit editing controls.
- Display the cable as a line connected to the exact port locations.
- Support multiple patch cables between the same two objects when they use different ports.
- Validate occupied ports and incompatible terminations.
- Moving equipment must move the visual cable endpoints while preserving the cable's port assignments.

Patch cables and fixed links must be visually distinguishable. Do not collapse fixed links into ordinary patch cable records.

9. END-TO-END PHYSICAL TRACING

Tracing is an essential feature in both view and edit modes.

- The user can select any port, patch cable, fixed link, or individual wire and request “Trace connection.”
- Highlight the complete known physical path and dim unrelated map objects and connections.
- Show an ordered path list with object names, port labels, patch cable IDs, fixed link IDs, wire IDs, and cable categories.
- Support navigation across maps. If the next part of a path is on another map, let the user open that map and continue viewing the highlighted path.
- Show where a path terminates, is disconnected, or cannot be resolved.
- Never infer a physical connection from visual proximity, group membership, rack membership, or a shared switch.
- Follow patch-panel internal mappings only when documented.
- Where a fixed link contains multiple wires, trace the specific wire mapping relevant to the selected port.
- Provide a way to clear tracing and return to the normal map view.

Example:
Switch A port 12
-> patch cable PC-012
-> Rack A panel PP-A port 12
-> fixed link FL-004, wire 12
-> Rack B panel PP-B port 12
-> patch cable PC-067
-> Office wall socket WS-02 port 1

10. FREE-FORM MAP EDITOR

- Create objects through a toolbar or context menu.
- Use a dedicated drag handle to move objects.
- Selecting an object must not accidentally move it.
- Support pan, zoom, grid snapping, selection, and fit-to-map.
- Support resizing where appropriate.
- Automatically update cable drawing endpoints when objects move, without altering connection records.
- Support object labels and annotations.
- Provide visual distinction between groups, racks, panels, switches, endpoints, fixed links, and patch cables.
- Cable colours must be configurable and readable against the canvas background.
- Avoid cable routes obscuring port labels where reasonably possible.

11. SAVE, LOAD, AUTOSAVE, BACKUP, AND VALIDATION

JSON import/export:
- Export the complete project to a human-readable JSON file.
- Import a project and validate it before replacing or merging with current data.
- Include all objects, groups, ports, fixed links, individual fixed wires, patch cables, internal mappings, maps, placements, labels, colours, and settings.
- Preserve IDs and connectivity through export/import.
- Include a schema version and migration path.

Autosave and backup:
- Autosave local edits to browser storage after a short idle delay.
- Indicate unsaved changes and save errors.
- Restore the most recent session when possible after refresh or accidental closure.
- Provide manual JSON export as a portable backup.
- Never claim that browser autosave replaces manual backup files.
- Do not silently overwrite a user-selected project or file.

Validation:
- Detect duplicate IDs and missing object/port references.
- Detect occupied ports and incompatible connections.
- Detect fixed links with missing endpoints or invalid wire mappings.
- Detect internal mappings that refer to nonexistent ports.
- Report unused ports without automatically treating them as errors.
- Present useful error messages and allow the user to navigate to the affected object.

12. UNDO AND REDO

Support undo/redo for:
- Object and group creation/deletion.
- Object movement and resizing.
- Patch cable creation, editing, reconnection, and deletion.
- Fixed link creation and explicitly confirmed fixed-wiring changes.
- Adding and deleting wires in a fixed link.
- Port label and property changes.
- Changes to internal port mappings.

Undo must restore the data model as well as the visual state. Deleting an object with connections must require confirmation and explain the consequences. Undo should restore affected objects and connections.

13. EXPORTS

Provide:
- JSON: complete editable project backup.
- PNG: image of the selected map.
- SVG: scalable vector image of the selected map.
- PDF: printable map and/or connection documentation.
- Printable connection table listing cable/link ID, category, source and destination, port labels, wire mapping, cable type, and optional length.

For large projects, allow selecting individual maps or a subset of infrastructure for export. Exports must preserve labels and make fixed links visually distinguishable from patch cables. Export functions must work offline.

14. SEARCH AND NAVIGATION

Search by:
- Group, location, map, rack, equipment, or object name/ID.
- Patch panel port label.
- Switch port label.
- Wall socket and endpoint port label.
- Patch cable ID.
- Fixed link ID or individual wire ID.

Selecting a result must navigate to a relevant map and highlight the matching object, port, or connection. Search and tracing must remain usable in mobile view mode.

15. USER INTERFACE LAYOUT

Desktop:
- Left sidebar: project/map navigation and object creation in edit mode.
- Main area: map canvas.
- Right sidebar: selected object, port, cable, or link details.
- Optional panel for trace results and validation warnings.

Mobile view mode:
- Responsive narrow-screen layout.
- Compact navigation and search.
- Object and connection details shown in a bottom sheet, drawer, or similarly phone-friendly panel.
- Large touch targets.
- No requirement to display the entire desktop sidebar layout on a phone.
- Prioritize browsing, searching, port inspection, and connection tracing.

Edit mode:
- Clear edit-mode indicator.
- Dedicated movement handles and explicit connection-editing actions.
- Confirm destructive operations and fixed-wiring changes.
- Avoid accidental edits from normal map browsing.

16. MVP ACCEPTANCE TESTS

The MVP is complete only when these scenarios work:

1. Create groups for two rooms and place racks, patch panels, and switches inside them.
2. Create a standalone patch panel outside a rack.
3. Create a fixed link between patch panels in different racks.
4. Configure a fixed link containing N wires and define each wire's endpoint mapping.
5. Verify that moving racks, groups, and panels does not change fixed-link endpoints or wire mappings.
6. Add or delete a fixed-link wire only through an explicit edit operation.
7. Add removable patch cables between individual switch and panel ports.
8. Trace from a switch port through a patch lead, a fixed-link wire, another patch panel, and a remote patch lead to a wall socket.
9. Display the complete trace across multiple maps and navigate between those maps.
10. Use view mode on a narrow mobile screen without accidentally editing infrastructure.
11. Enter edit mode and make changes; undo and redo them successfully.
12. Refresh the browser and recover the autosaved project.
13. Export JSON, import it again, and verify all IDs, port mappings, maps, groups, and cable records.
14. Export PNG, SVG, and PDF.
15. Export a connection table containing both fixed-link wire mappings and patch cable connections.
16. Detect and report invalid endpoints, occupied ports, and broken references.

17. FUTURE ENHANCEMENTS — OUTSIDE MVP

Do not delay the MVP to implement:
- Detailed rack elevation with front/rear views and rack-unit placement.
- Floor-plan backgrounds and automatic layout.
- Cable bundles, conduits, fibre core/strand management, and route-length calculations.
- CSV import/export and reusable equipment templates.
- Maintenance history, cable testing records, and label printing.
- Multi-user editing, permissions, and audit logs.
- Database-backed storage or synchronization.
- NetBox integration, SNMP discovery, and live device status.
- Advanced filtering and custom object types.

18. IMPLEMENTATION ORDER

1. Define and document the versioned JSON schema and connectivity rules.
2. Implement groups, maps, equipment objects, ports, and stable IDs.
3. Implement fixed links with individual wire mappings and strict editing rules.
4. Implement removable patch cables and port occupancy validation.
5. Implement end-to-end tracing across equipment and maps.
6. Implement view/edit modes and responsive mobile view mode.
7. Implement autosave, JSON import/export, backup, undo, and redo.
8. Implement PNG, SVG, PDF, and connection-table exports.
9. Complete the acceptance tests and document installation and recovery.

Build a functional, tested MVP rather than a static mockup. Correct physical connectivity, safe fixed-link editing, dependable data persistence, and mobile-friendly view mode are higher priorities than decorative styling or advanced features.
